## 1. 先抓住这篇论文最重要的一句话

> 【本文解释】在等待当前真实 API 返回时，预测其可能的返回值，据此提前启动后续真实调用；等真实执行确定后，再复用符合真实调用需求的分支。

关键不是让小模型取得最终决策权，而是让原本要做的真实工作尽早开始。Actor 的响应仍然决定正式状态怎样前进；Speculator 的猜测只负责创造提前工作的机会。

但这里有一个必须加上的限定：提前执行与顺序执行是否等价，依赖调用语义、环境状态、随机性和副作用隔离。不能把“调用名与参数相同”不加条件地解释为通用正确性保证。

这篇论文对后续阅读的价值，是提供一套统一抽象、简洁算法和收益—成本分析；它没有提供覆盖任意有状态工具的完整事务协议。

## 2. 用 V 型科研模式还原它的研究逻辑

| 层次 | 这篇论文做了什么 | 证据与边界 |
|---|---|---|
| 表象 | Agent 完成一次任务需要很久，交互中有显著等待 | 引言给出典型任务时间；具体测量见实验。引言的任务时间不是本文统一实验结果 |
| 技术边界 | 加快某一次 LLM 生成，仍可能留下串行 API 和环境等待 | 原文把 LLM、工具和人类响应统一为 API |
| 关键约束 | 下一次调用的构造依赖当前返回；但部分返回可被便宜地预测 | 预测是否导向相同下一调用，由命中率实验检验 |
| 方案 | 在预测状态上预启动真实调用，把计算或工具执行与当前等待重叠 | Algorithm 1、棋类时序图 |
| 回到验证 | 测量调用命中、延迟、分支成本；讨论可逆条件 | 不同场景证据不对称；不能用命中率代替完整端到端实验 |

【本文解释】这里的“机理”是**数据依赖与提交依赖可以分开：工作可提前做，结果要等依赖验证后才进入正式执行**。它是一种系统层面的约束分析，不是对模型为什么理解某类任务的神经机理解释。

还要区分两种“为什么”：

1. **为什么能加速？** 因为提前启动的有效工作覆盖了一部分关键路径等待。
2. **为什么能猜中？** 论文用若干领域实验说明预测有一定可行性，但没有给出普遍的动作可预测性定律。

第一问的系统逻辑比较清楚；第二问仍主要由经验结果支撑。不能因为论文的 V 型叙事完整，就把两问都视为已被理论解决。

## 3. 最容易读错的符号：这里的 action 不总是工具调用请求

论文从 Agent/MDP 视角引入状态和动作，又从系统视角用 API 表示一步：

\[
(h_t,q_t)=\pi(s_t),\qquad
\bar a_t\leftarrow h_t(q_t),\qquad
a_t=\operatorname{await}(\bar a_t),\qquad
s_{t+1}=f(s_t,a_t).
\]

| 符号 | 在论文算法中的含义 | 例子 |
|---|---|---|
| \(s_t\) | 当前正式状态 | 棋盘；对话与检索历史 |
| \(\pi\) | 从状态构造调用目标与参数 | 构造 LLM prompt；选择 Search 查询 |
| \(h_t\) | 被调用的 API | LLM 推理服务；Search；Lookup |
| \(q_t\) | 调用的参数 | 完整 prompt、查询字符串等 |
| \(\bar a_t\) | future，即尚未完成的真实请求句柄 | 正在执行的推理或检索任务 |
| \(a_t\) | 真实 API 的返回值 | LLM 给出的棋步；搜索工具返回的内容 |
| \(\hat a_t\) | 对该返回值的预测 | 猜测棋步；猜测搜索内容 |
| \(f\) | 接收返回值后如何更新状态 | 更新棋盘；将真实 observation 加入历史 |
| \(\mathcal C\) | 将调用 \((h,q)\) 映射到 future 的缓存 | 已完成或仍在运行的预启动调用 |

因此，读到“预测 \(a_t\)”不能一律翻译成“小模型生成工具名和参数”。在棋类场景，\(a_t\) 是 LLM 返回的棋步；在 HotpotQA，它可能是 Wikipedia 返回内容。

**Actor 也不必总是大模型。** 在这个抽象中，它可以是权威响应来源，包括真实工具、另一位玩家或人类。Speculator 也不必是小模型；棋类实验用的是同一 GPT-5 的不同 reasoning effort。

【本文解释】所谓“权威”只表示相对于指定串行 baseline 的参照地位，不意味着 Actor 的决定一定符合用户目标，也不意味着它绝不会幻觉。

原文定位：[Framework 的 API 抽象][S2]，PDF 第 4 页。

## 4. 用一个具体例子看完整时序

### 4.1 先看一次命中

【本文解释：教学例子，不是论文测量】Agent 正在回答“某位作家的出生城市属于哪个国家”。当前调用是 `Search(作家姓名)`：

- 当前搜索需要 \(B=8\) 秒；
- Speculator 用 \(G=1\) 秒猜测搜索返回中会出现“出生于城市 X”；
- 按这个预测，下一次调用将是 `Search(城市 X)`，耗时 \(C=5\) 秒；
- 暂假设调用参数构造和验证开销可忽略，且搜索结果在这段时间内稳定。

| 时刻 | 正式执行 | 投机执行 | 可以提交什么 |
|---|---|---|---|
| 0 秒 | 启动 `Search(作家姓名)` | 启动返回内容预测 | 尚不能提交预测内容 |
| 1 秒 | 当前搜索仍未完成 | 得到预测，在预测状态上构造并启动 `Search(城市 X)` | 后续结果只能暂存 |
| 6 秒 | 当前搜索仍未完成 | `Search(城市 X)` 完成，结果留在缓存 | 仍不能因为分支完成就宣告两步完成 |
| 8 秒 | 收到真实搜索结果，更新正式历史；由正式状态决定下一调用 | 若正式调用恰好为 `Search(城市 X)`，找到对应缓存 | 在复用条件成立时，接受已完成的真实工具结果 |

串行要 \(8+5=13\) 秒；这里经过验证的两步执行在第 8 秒完成，节省 5 秒。

注意两个区别：**预测内容不是正式 observation；分支完成不是正式 commit。**

### 4.2 如果猜错

假设第 8 秒得到真实结果后，正确的下一调用是 `Search(城市 Y)`：

1. 正式历史只接受 `Search(作家姓名)` 的真实返回。
2. 城市 X 分支不进入正式轨迹，其工作可能浪费。
3. 第 8 秒启动城市 Y 的正常调用。
4. 如果没有资源竞争、错误分支副作用或恢复开销，退回串行耗时；这些条件不满足时，可能更慢。

“拒绝错误结果”只解决轨迹污染的一部分问题；如果错误分支已经修改共享环境，还必须处理它留下的影响。

### 4.3 如果分支尚未完成或预测太晚

命中缓存并不意味着结果已经可读。Algorithm 1 缓存的是 future，命中后可能仍要 `await`。如果下一工具特别慢，提前执行只消掉它的一部分等待。

如果真实调用先于 Speculator 返回，合理的运行时应允许正式路径及时继续。论文伪代码按字面先 `await` Speculator 再 `await` Actor，没有明确展开这一竞速和取消机制；后续必须检查实现。

### 4.4 把例子抽象为局部收益

在“命中、无争用、验证可忽略、Actor 先结束时可以直接继续”的两调用局部模型中：

\[
T_{\rm seq}=B+C,
\]

\[
T_{\rm spec}=\max\{B,\min(G,B)+C\},
\]

\[
\Delta T=\min\{(B-G)_+,C\}.
\]

这条**本文推导**说明：收益同时受“提前启动了多久”和“下一步有多少工作可覆盖”限制。它不是论文全轨迹定理的替代品，但很适合先建立正确直觉。第 12 节会解释它与论文附录某个表达式的差异。

## 5. 按 Algorithm 1 还原系统，而不是凭摘要补出一个系统

算法位于 PDF 第 5 页；本地定位：[Framework 中的 Algorithm 1][S3]。

### 5.1 实际写出的逻辑

1. 从正式状态 \(s_t\) 构造本步真实调用 \((h_t,q_t)\)。
2. 如果缓存有这个调用，则取得 future，等待真实返回，更新正式状态，然后 `continue`。
3. 如果没有缓存，启动本步真实调用，同时运行 Speculator。
4. Speculator 给出 \(k\) 个当前返回值的预测。
5. 对每个预测，计算假设状态 \(\hat s_{t+1}^{(i)}=f(s_t,\hat a_t^{(i)})\)。
6. 在假设状态上构造下一调用 \((\hat h_{t+1}^{(i)},\hat q_{t+1}^{(i)})\)，预启动该调用，把 future 存入缓存。
7. 等待当前真实返回 \(a_t\)，只用真实返回更新正式状态。
8. 下一轮再次从正式状态构造调用，通过 cache lookup 决定能否复用。

### 5.2 这里有三件容易忽略的事

**第一，原始抽象算法验证的是“真实下一调用是否命中缓存”。** 它并不要求预测 observation 的整段文本与真实 observation 逐字相同。只要两者导向同一下一调用，且复用语义成立，就可能命中。棋类实例则直接比较预测棋步与真实棋步，这是该领域的具体校验方式。

**第二，命中分支执行的通常仍是真实 API。** Speculator 负责猜测输入依赖；提前做下一步工作的可以是原 Actor 模型或真实工具，不应把它理解成“把小模型输出直接顶替大模型输出”。

**第三，cache-hit 分支执行完后直接 `continue`。** 这个单步算法在该轮没有重新打开一个投机窗口。附录的命中次数递推利用了这一点。它是具体策略的限制，不是动作投机的普遍限制。

### 5.3 论文没有在伪代码里具体落实的部分

- 缓存 key 的规范化、完整请求上下文和有效期。
- 对共享状态工具的隔离、读写依赖记录和原子提交。
- 拒绝分支的取消、错误和超时处理。
- Actor 比 Speculator 更早返回时的竞速规则。
- 多个分支得到同一调用时的去重生命周期。
- 接口限流、并发排队、额外计费及资源回收。

这些不等于代码一定缺失，但不能从抽象伪代码推断作者已实现了通用解法。论文关于副作用的讨论给出了前提与可选手段；本轮尚未核查代码如何实现。

## 6. 它为什么声称 lossless？究竟在哪个意义上成立？

### 6.1 先分清四种保证

| 保证 | 含义 | 能否仅靠“任务成功率差不多”证明 |
|---|---|---|
| 逐轨迹一致 | 相同初始条件和随机数耦合下，正式动作/观察序列相同 | 不能 |
| 分布一致 | 输出或轨迹的概率分布与串行 baseline 相同 | 不能 |
| 环境与外部行为等价 | 正式状态及约定范围内的可见副作用符合串行语义 | 不能 |
| 任务指标相当 | 测试集成功率等统计指标没有明显下降 | 只能支持这个较弱的经验结论 |

【作者陈述】引言强调 as-if-sequential 语义；棋类段落进一步称轨迹与非投机执行相同。正文的主要理论结果是延迟和成本分析，并不是一套对任意有状态 API 的完整语义保持证明。

### 6.2 一个能解释算法正确性的充分条件集合

下面是**本文重建的充分条件**，比原文两条运行假设展开得更细，不声称是作者逐字给出的定理：

1. 正式状态由真实返回更新，预测状态与正式状态隔离。
2. 下一次正式调用仍由真实历史按 baseline 的策略决定；不能只因为猜中了一个前缀就跳过后续决策。
3. 被复用调用与正式所需调用具有相同的有效输入，包括会影响返回值的上下文或环境依赖。
4. 提前执行没有改变该调用相对于串行执行的语义；失败分支也没有污染共享资源或外部可见状态。
5. 如果 API 或策略随机化，需要明确是分布保持还是同随机数轨迹保持，并保证挑选缓存样本不会引入额外选择偏差。
6. 提交顺序和恰好一次的副作用满足 baseline 的要求；过期缓存不得跨状态误用。

在这些条件下可以做归纳解释：假设两边正式状态相同，则构造相同的本步正式请求；未命中走原调用，命中取得语义等价的返回；相同的状态转移保持下一状态等价。这样逐步推进，才能建立 as-if-sequential 的论证。

### 6.3 为什么调用名、参数相同还不够

【本文反例】`get_inventory(product_id=7)` 在第 1 秒库存为 10，第 8 秒被其他用户买走后库存为 0。两次请求参数完全相同，早读结果却不等于串行时刻的读取结果。**只读不等于跨时间可复用。**

再如，提前执行 `run_tests()` 时读的是修改前代码；正式路径先改了代码再调用同名命令。命令字符串一样，依赖的文件状态不同。

因此，某些工具需要在调用参数之外验证状态或读集；到底需要整个状态、相关依赖的版本还是其他充分摘要，取决于具体语义。第一篇没有把它定义成统一检查机制，这正是后面读 AOSpec 时要带着的问题，而不是现在就能宣布的新颖性。

### 6.4 “可撤销”也需要说清楚观察范围

| 情况 | 能说明什么 | 不能自动说明什么 |
|---|---|---|
| 在独立棋盘副本上走一步 | 错误分支可丢弃 | 不涉及真实世界写副作用 |
| 幂等写操作 | 重复写可能不会再改变状态 | 提前写一次一定符合当前正式状态 |
| 下单后退款 | 业务上可能补偿金额 | 用户没有看到订单、库存没有占用、没有邮件和手续费 |
| 改 OS 参数后由 Actor 覆盖 | 最终参数可回到 Actor 决策 | 覆盖前的运行表现和历史已经被撤销 |

论文提到 rollback 和 roll-forward repair；后者可能只满足某种业务补偿语义，不能天然等同于严格不可观察的回滚。OS 实验也被作者明确单列为 **lossy extension**。

## 7. 理论部分怎样读：先学结构，再核查公式

### 7.1 Breadth：同一窗口猜多个候选

【作者陈述】假设每个候选以独立概率 \(p\) 导向正确下一调用，则：

\[
p(k)=1-(1-p)^k.
\]

该公式不是任意 top-k 列表的通用命中率公式。同一个模型输出的候选可能相关；在固定状态下，互异的候选调用匹配某一个唯一目标时，其事件还可能互斥。应先核对事件定义和独立性，再决定用理论 \(p(k)\) 还是经验 union hit rate。

作者还假定：预测耗时服从 \(\mathrm{Exp}(\alpha)\)，真实调用耗时服从 \(\mathrm{Exp}(\beta)\)，\(\alpha>\beta\)；这些随机量和命中事件独立，\(f\) 与 \(\pi\) 开销可忽略。注意 \(\alpha,\beta\) 是**速率**，平均耗时分别为 \(1/\alpha,1/\beta\)。

论文 Proposition 1 的长序列结果为：

\[
\frac{\mathbb E[T_{\rm spec}]}{\mathbb E[T_{\rm seq}]}
\longrightarrow
1-\frac{p(k)}{1+p(k)}\frac{\alpha}{\alpha+\beta}.
\]

应怎样理解它的结构？

- \(p(k)\)：候选覆盖真实下一调用的程度。
- \(p(k)/(1+p(k))\)：与“命中后没有新的投机窗口”的节奏有关。
- \(\alpha/(\alpha+\beta)\)：与预测和真实调用的相对速度有关。

附录令 \(S_n\) 为 \(n\) 个潜在窗口中的期望命中数，使用：

\[
S_n=p(k)(1+S_{n-2})+(1-p(k))S_{n-1},
\]

并得到：

\[
S_n=\frac{p(k)}{1+p(k)}n+
\frac{p(k)^2}{(1+p(k))^2}\bigl(1-(-p(k))^n\bigr).
\]

这能帮助理解为什么不是每一步都有投机收益，但不能跳过“每次命中到底省多少时间”的核查。

**【推导审查】第 12 节发现附录两步完成时间的表达式与等待验证的语义存在冲突。因此，本笔记把上述长序列公式记录为作者结果，不把其精确数值和 50% 界当成已经独立验证的定理。**

无论该推导问题如何澄清，论文所说的 50% 上界都针对特定单步策略与延迟模型；不能直接称为所有 Agent 动作投机的上限。节省 50% 时间对应 2 倍速度，也不要混淆“时间降低比例”和“加速倍数”。

### 7.2 Cost：增加宽度为什么会昂贵

【作者陈述】用 \(\tilde k\) 表示去重后的实际分支数，在简化计费假设下，相对额外成本的渐近式为：

\[
\frac{\mathbb E[M_{\rm spec}-M_{\rm seq}]}{\mathbb E[M_{\rm seq}]}
\longrightarrow
\tilde k-
\left(\tilde k+\frac{\alpha}{\alpha+\beta}\right)
\frac{p(k)}{1+p(k)}.
\]

最有用的直觉：收益随候选覆盖趋于饱和，错误分支却消耗资源。去重和选择性发射比无条件增大 \(k\) 更有价值。

实际 API 的输入/输出 token 单价、缓存计费、取消后的收费和不同模型价格并不统一；自托管下的 GPU 排队成本也不能由固定每秒 token 费率自动表示。原文简化式还依赖前面的命中统计与时间模型，后续不宜直接拿它做预算承诺。

### 7.3 Confidence：第一篇已经做了选择性投机

【作者陈述】排序后前 \(m\) 个分支的命中概率写为：

\[
q(m;\mathbf p)=1-\prod_{j=1}^{m}(1-p^{(j)}).
\]

在其有限时域模型内，选择规则是：

\[
m_t^*\in\arg\max_m\{q(m;\mathbf p)\Delta_t-cm\}.
\]

其中 \(\Delta_t\) 是考虑后续机会后的价值差。新增分支是否值得，取决于**新增命中概率带来的价值能否覆盖新增成本**。

论文在棋类实验中实际使用的是预测正确率超过 50% 才继续执行的简单阈值近似；这不是运行完整动态规划后测得的最优策略。正文所说的平稳常数应联系附录的无限时域平均收益设定理解，有限时域即使分布平稳也有终止效应。

【推导审查】附录的平稳收益表达式还混合了“固定分支数”和“观察置信度后选择分支数”两类策略，详见第 12.3 节。它不影响“已有 confidence-aware 思路”这一文献事实，但影响能否照搬某个最优值公式。

### 7.4 Depth：第一篇也已经分析多步扩展

作者考虑固定真实耗时 \(a\)、预测耗时 \(b<a\) 的深度策略，给出时间降低比例：

\[
\frac{T-1}{T}p\left(1-\frac ba\right),
\]

并分析误投机开销中的 \((1-p)(a/(2b)-1/2)\) 项。正文称该特定推进/剪枝策略的活跃分支数不随任务长度 \(T\) 增长；这不等于任意多分支深树都没有组合爆炸。

**阅读结论：不能说 Speculative Actions 完全没有研究多步、动态策略或置信度。** 更准确地说，其核心演示算法是单步多候选，同时含有扩展分析和选择性分支实验。深度策略的一般语义、调度和工程可复现程度仍需另查。

### 8.5 OS tuning：学习它的价值，也保留“有损”标签

调节 Linux CFS 的 `min_granularity`，使用 `sysbench cpu`。Speculator 每秒提出更新，Actor 约每 10–15 秒作一次较深决策，Actor 返回后覆盖临时参数。

环境：CloudLab 机器，2×Intel Xeon Silver 4114、192 GB RAM、Ubuntu 22.04、Linux 5.15；16 个 sysbench 线程绑定到两个 CPU 核。这里是在记录论文实验环境，不是当前机器或当前 Linux 的配置建议。

| 比较 | 论文报告 |
|---|---|
| 20 秒恢复实验的平均 workload p95 | Untuned 102.97 ms；Actor-only 54.00 ms；联合系统 37.93 ms |
| 收敛时间 | Actor-only 约 200 s；联合系统约 13 s |
| 各自在收敛时的累计费用 | Actor-only 2.18 cents；联合系统 0.17 cents |

## 9. 它与 speculative decoding 是什么关系？

Speculative Actions 的相关工作借鉴了 token-level 的 draft-and-verify 思路。经典 speculative decoding 的核心是通过目标模型验证和采样校正，保持目标生成分布；它不只是比较两个模型是否恰好独立生成同一个 token。[Leviathan 等人的原论文页面](https://proceedings.mlr.press/v202/leviathan23a.html)

| 维度 | 经典 token-level speculative decoding | 本文 Speculative Actions |
|---|---|---|
| 投机单位 | token 序列 | API 返回及其诱导的后续调用 |
| 被隐藏的等待 | 逐 token 自回归推理 | 跨调用的串行依赖和响应延迟 |
| 正式参照 | 目标模型的条件生成分布 | 串行 Agent/环境的调用和状态语义 |
| 验证重点 | 目标模型验证与接受/拒绝采样规则 | 真实状态下是否需要该调用，以及提前执行结果是否仍可复用 |
| 主要实现问题 | 模型前向、draft/target 配合与推理状态 | future/cache、工具副作用、外部状态、异步调度 |
| 分支错误代价 | 额外模型计算 | 模型或工具计算、请求计费，以及可能的状态恢复 |

【本文解释】两者可以组合，因为处理的依赖层次不同；但组合收益不一定相乘。若 token decoding 变快，动作投机可利用的模型等待窗口也会改变。到底增加还是减少收益，取决于预测时点、工具延迟和共享资源；需要时序测量，不能凭“两个都加速”下结论。

这也说明为什么“用 speculative decoding 加速 Agent”必须继续追问：加速的是模型内部 token，还是工具动作的提前执行？

## 11. 阅读后留下的可检验问题：尚不是选题

### 11.1 有效命中是否比裸命中率更能解释加速？

**来源**：论文多个实验用调用匹配率证明潜在价值，但真实时序决定了命中是否及时、能省多少工作。

**最小诊断**：在同一批真实轨迹上记录当前调用起止、预测完成、预执行开始/结束、验证完成和正式提交时间。统计：

- 原始调用命中率；
- 在正式需要前已提前开始的有效命中率；
- 命中时实际消掉的等待时间；
- 未命中、预测太晚、资源争用和验证的额外耗时。

**可能推翻我们期待的结果**：在控制模型和任务后，简单命中率已足够解释几乎全部收益；更复杂指标或策略没有稳定增益。还必须检查 SPORK、AOSpec 等是否已经系统解决该问题。

### 11.2 `(h,q)` 匹配在哪些环境足够，在哪些环境不够？

**来源**：算法 key 与共享状态问题。

**最小诊断**：先用可控工具区分纯函数、稳定只读、随时间变化只读、有状态写入四类，保持工具名与参数不变，受控改变依赖状态，检查复用是否偏离串行语义。

**可能推翻我们期待的结果**：目标任务的工具语义本来足够稳定，或者现成快照机制已经以极低成本彻底解决问题。此时不能只凭构造反例就声称有重要系统缺陷。AOSpec 是必须优先对照的工作。

### 11.3 公平资源预算下，投机还是否获益？

**来源**：并发 API 的延迟/费用与本地 GPU 的竞争不是一回事。

**最小诊断**：在相同模型、上下文和请求负载下比较串行与不同投机宽度，测 Actor 延迟、任务延迟、总 token、峰值并发和吞吐；后续再考虑每任务 GPU-seconds。

**可能推翻我们期待的结果**：常见负载下资源竞争可以忽略，已有简单并发上限就达到了同样效果。先测瓶颈是否存在，再设计调度系统。

### 11.4 预测能力究竟来自任务知识，还是行为一致性？

**来源**：HotpotQA 中较强 Speculator 不必更高匹配率，同模型低预算在 Chess 有效。

**最小诊断**：固定 Actor 与任务，对 Speculator 的模型、prompt 和预算做受控改变，分别测调用一致性和任务能力，不把二者混成一个 accuracy。

**可能推翻我们期待的结果**：差异主要来自少数格式或解析细节，统一格式后消失；或训练式自投机、memory 已经解决该差异。必须先读完 Speculate While You Reason 和 Speculate with Memory。

以上都是定位证据的工作，不是现在就要实现的四个新系统。

### 12.1 附录 A 的“两步完成时间”遗漏验证等待

原文设预测耗时为 \(A\)，前后两个真实调用耗时为 \(B,C\)，三者独立；命中时写出：

\[
R=B+C,\qquad S=C+\min\{A,B\},\qquad R-S=(B-A)_+.
\]

来源：PDF 第 14 页，[本地附录 A 第 12 行起][S10]。这里的 \(A\) 等于本笔记前文的 \(G\)。

**【推导审查】如果完成两步的含义是“前一步已验证、后一步已可正式提交”，还必须等待 \(B\) 完成。** 在允许 Actor 先结束时立即继续的模型下，应有：

\[
S_{\rm gated}=\max\{B,C+\min(A,B)\},
\]

\[
R-S_{\rm gated}=\min\{(B-A)_+,C\}.
\]

最直接的反例是 \(A=1,B=10,C=1\)：

| 量 | 原文局部表达式 | 加入验证屏障的两步模型 |
|---|---:|---:|
| 串行完成 | 11 秒 | 11 秒 |
| 投机两步完成 | 2 秒 | 10 秒 |
| 节省 | 9 秒 | 1 秒 |

在第 2 秒，当前真实调用要到第 10 秒才回来，无法知道猜测是否命中。原式可能表示后续分支自身完成时间，但不能无条件表示经过验证的两步完成时间。

同一指数分布设定下，对**孤立的命中两步块**，本文得到：

\[
\mathbb E[\min\{(B-A)_+,C\}]
=\frac{\alpha}{2\beta(\alpha+\beta)}.
\]

理由是 \(\Pr(A<B)=\alpha/(\alpha+\beta)\)；在 \(A<B\) 条件下，由无记忆性，\(B-A\) 与独立的 \(C\) 都服从 \(\mathrm{Exp}(\beta)\)，两者最小值均值为 \(1/(2\beta)\)。

这与附录使用的 \(\alpha/[\beta(\alpha+\beta)]\) 不同。**不能据此把整条轨迹的公式简单除以二**：多步过程的残余服务时间、命中窗口、缓存状态和调度策略还需重新推导。当前确认的是局部完成时间与验证条件不一致；全局定理如何修订需要进一步分析。

### 12.2 理论中的“谁先结束就继续”与伪代码的等待顺序

Algorithm 1 先发起 Actor future，再 `await` Speculator，最后才 `await` Actor。指数延迟即使均值上 Speculator 更快，也仍有 \(A>B\) 的事件。

在这些事件中，按伪代码字面执行会等较慢的预测；附录却使用 \(\min(A,B)\)，相当于允许较早完成的一方推动下一步。

因此需要区分：

- **算法文字所描述的同步等待顺序**；
- **系统设计意图中的并行预测**；
- **理论模型中的竞速/回退规则**；
- **真实代码实际执行的事件顺序**。

这可以是伪代码省略了运行时细节，但目前不能直接把算法、证明和代码当作完全一致。后续先记录事件日志检验，无需急于改造系统。

### 12.3 平稳策略：固定 \(m\) 与观察 \(\mathbf p\) 后决策不同

附录 C.3 的 Corollary 6（PDF 第 23 页）先给出：

\[
g^*=\max_m\frac{\bar q(m)\ell-cm}{1+\bar q(m)},
\]

随后又允许策略根据观察到的置信度 \(\mathbf p\) 选择 \(m^*(\mathbf p)\)。前一个表达式只对固定分支数取最大，未包含一般的置信度依赖策略。

**【本文构造的反例】** 取 \(k=1\)，在每个可投机窗口中置信度 \(P\) 以各 1/2 的概率取 0 或 1；收益 \(\ell=1\)，成本 \(c=0.4\)。完全沿用附录的两模式与单位 epoch 计数：

- 固定从不启动：平均收益 0。
- 固定总启动：平均每个窗口周期收益 \(0.5-0.4=0.1\)，平均周期长度 \(1+0.5=1.5\)，长期平均收益约 0.0667。
- 观察到 \(P=1\) 才启动：平均周期收益 \(0.5-0.5\times0.4=0.3\)，平均周期长度仍为 1.5，长期平均收益为 0.2。

可观察置信度的策略严格优于公式中最优固定 \(m\)。因此该表达式不能直接代表其所宣称的一般自适应最优值。

在这个两模式模型中，对于平稳策略映射 \(\mu(\mathbf P)\)，可先写成：

\[
g(\mu)=\frac{\ell\,\mathbb E[q(\mu(\mathbf P);\mathbf P)]
-c\,\mathbb E[\mu(\mathbf P)]}
{1+\mathbb E[q(\mu(\mathbf P);\mathbf P)]},
\]

再对策略映射优化。对应的平均收益 Bellman 关系可写为：

\[
g^*=\mathbb E\left[\max_m\{q(m;\mathbf P)(\ell-g^*)-cm\}\right].
\]

这里的调整针对数学表述，不意味着阈值策略毫无价值，也不意味着修正公式本身就足以构成一篇新的系统论文。先学会把“合理策略结构”和“声称的精确最优表达式”分开审查。

### 12.4 本轮做过的最小数值核查

仅使用 Python 标准库，未调用任何模型或工具 benchmark。

1. 检查 \((A,B,C)=(1,8,5),(1,10,1),(1,10,20),(12,10,4)\)，确认带验证屏障的完成时间与截断收益恒等式一致。
2. 固定随机种子 `20260908`，采样 200,000 个独立两步块，取 \(\alpha=1,\beta=0.2\)。原式的未截断节省样本均值为 4.16663；带验证等待的样本均值为 2.09006，接近相应解析值 4.16667 与 2.08333。
3. 计算前述平稳策略例子，得到固定策略 0.06667，自适应策略 0.2。

可自行重跑的局部核查代码：

```python
from random import Random

for A, B, C in [(1, 8, 5), (1, 10, 1), (1, 10, 20), (12, 10, 4)]:
    sequential = B + C
    gated = max(B, min(A, B) + C)
    saving = min(max(B - A, 0), C)
    assert sequential - gated == saving
    print(A, B, C, sequential, gated, saving)

rng = Random(20260908)
alpha, beta, n = 1.0, 0.2, 200_000
uncapped = capped = 0.0
for _ in range(n):
    A = rng.expovariate(alpha)
    B = rng.expovariate(beta)
    C = rng.expovariate(beta)
    uncapped += max(B - A, 0)
    capped += min(max(B - A, 0), C)
print(uncapped / n, capped / n)
print(alpha / (beta * (alpha + beta)))
print(alpha / (2 * beta * (alpha + beta)))

fixed = max(0, (0.5 - 0.4) / 1.5)
adaptive = (0.5 - 0.5 * 0.4) / 1.5
print(fixed, adaptive)
```

这些结果是**局部模型核查，不是 Speculative Actions 的复现实验，不是新方法的实验结果**。

## 13. 站在导师视角，怎样评价它的贡献与证据？

值得学习的地方：

- 从多种真实交互场景抽出统一的 API 依赖结构，而不只在某个 benchmark 上增加模块。
- 明确保留正式 Actor 的参照角色，并意识到副作用是动作投机区别于纯文本推理的重要边界。
- 不只报告命中率，也讨论宽度、深度、费用和选择性启动，使后续工作有比较坐标。
- Chess 的真实时间实验表明，预测并预计算有机会转化成实际收益。

需要补强或澄清的地方：

- 对状态、随机性与可见副作用的语义约束还没有形成完整通用协议。
- 不同领域的指标和实验深度不统一，电商、HotpotQA 的匹配率不能替代端到端收益与任务质量。
- 理论对调度、独立性和资源的简化很强，而且存在本节已列出的局部推导疑点。
- 自适应 predictor 的来源、校准和成本，需要更明确的可复现说明。
- 多步扩展的讨论不能替代复杂状态环境下的系统验证。

评价应该是：**这是一篇有启发性的框架与概念验证工作，值得作为机制 baseline；其所有 lossless 表述、理论常数和跨领域收益，需要按场景逐项审查。** 发现疑点不否定其核心并行思想，也不自动证明我们有了顶会选题。

## 14. 对你现阶段实现能力的要求

此刻不需要先训练一个新的 Speculator，也不需要从零写分布式系统。读懂这篇论文，优先掌握四个小概念：

1. **Future 与异步任务**：请求发起后还没完成，为什么仍可以保存并复用其句柄？
2. **状态副本与正式状态**：哪段历史允许接收预测，哪段只能接收真实返回？
3. **调用匹配与有效缓存**：命中了字符串 key，为什么还可能是无效结果？
4. **关键路径计时**：从任务开始到正式完成的时间，为什么不等于模型/工具耗时直接求和？

进入代码阶段时，可先选纯只读或可复制环境，把日志和 baseline 跑通，再接入真实模型。先学习如何准确测量和解释一次命中，通常比立即增加 memory、深度树或训练管线更有用。这是实现路径建议，本轮没有执行这些项目。
