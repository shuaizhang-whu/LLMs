# 03 · PASTE：历史模式、工具预执行与 LLM 联合调度

阅读日期：2026-09-08。论文：**Parallelizing Tool Execution and LLM Generation for Low-Latency Agent Serving**。PASTE = Pattern-Aware Speculative Tool Execution。

来源：本地 LaTeX 全部正文，核对关键实验图；[官方版本记录](https://arxiv.org/abs/2603.18897)显示首版 2026-03-19，v3 为 2026-06-16。本笔记针对当前本地标题与设计，不混用旧版结论。本轮不运行代码，也不重新检索开源状态。

## 1. 对选题最重要的结论

**PASTE 不只是“用历史 pattern 猜工具”。它把具体参数绑定、选择性工具投机、结果隔离以及 LLM 负载调度结合起来。**

因此，下列宽泛 idea 已被覆盖，不能直接作为我们后续的主要创新：

- 从历史轨迹挖掘工具模式，并从当前 observation 提取参数。
- 按置信度、预期可隐藏时间和资源需求选择投机候选。
- 给正式调用更高优先级，限制或抢占投机工作。
- 考虑工具加速引起的 LLM 请求突发，通过联合调度保留端到端收益。

DSP 留下的“匹配概率不是实际收益”和“并发可能抵消加速”问题，**PASTE 已在机制层面正面处理**。剩余空间只能进一步落到具体条件、策略差距或保证上。

## 2. 机制与完整时序

### Pattern 到底存什么？

一条记录包含：**近期事件上下文、未来工具目标、参数映射器、经验置信度**。

事件分成两部分：稳定 signature 用于匹配控制流程，例如工具类型和成功/失败状态；payload 保存 URL、文件名等当前具体内容。离线先挖短事件模式，再从历史实例归纳简单映射规则，例如字段读取、选择第几个结果、字符串规范化。运行时匹配近期事件后，才从当前 payload 绑定参数。

例如 `search 成功 → visit` 不是直接缓存旧 URL，而是预测 `visit(当前搜索结果中的第一个 URL)`；失败后的模式可以选择下一个结果。这比“仅预测工具名”更具体，也不同于训练一个小 LLM 自由生成全部参数。

### 用 search → visit 走一遍

假设搜索结果已经返回，LLM 还要思考 4 秒才发出下一调用，访问网页需要 6 秒。以下时间仅为解释示例。

1. Pattern Analyzer 从搜索结果提取 URL，产生完整 `visit(url)` 候选。
2. Scheduler 检查参数完整、工具安全、预期收益和资源预算，通过后立即访问网页，与 LLM 思考重叠。
3. 4 秒后，LLM 正式发出调用。系统比较**规范化后的工具名和参数**。
4. 若命中且投机仍在执行，将它升级为正式工作，等待剩余约 2 秒；若已经完成，直接复用结果。命中不是永远零等待。
5. 若不匹配，执行正式调用，未使用的投机结果过期丢弃。投机输出不会提前加入正式历史。
6. 获得正式工具结果后，下一轮 LLM 请求进入调度队列；不一定立刻送入 GPU。

理想无竞争情况下，这一段从 10 秒变为 6 秒。实际收益还要扣除调度、排队和资源竞争影响。

**不是整条 macro 的免验证提交**：历史短模式用于预测未来调用，正文的复用边界仍是 LLM 发出匹配的正式调用，不能解释为验证第一步就接受整条链。

## 3. 两个调度器分别管什么？

| 组件 | 决策 | 已考虑的信息 |
|---|---|---|
| Tool Speculation Scheduler | 哪些候选提前运行，哪些压制/抢占 | 参数可执行性、安全策略、置信度、可隐藏工具时间、资源需求和预算 |
| LLM–Tool Co-Scheduler | 哪个已就绪的 LLM turn 进入引擎、怎样控制负载 | 工具完成/命中信息、会话进度、预期收益、服务时长、batch、上下文和 KV 压力 |

工具侧优先选择单位资源预期效用较高的候选，正式工作优先。LLM 侧给出的优先级形式是：

`priority = ExposedToolGain / LLMPressure + Aging`

同时用 decode 与 KV 压力构成的分数控制负载区间。Aging 用于公平性。

**论文事实与边界**：设计已经考虑收益和竞争；但正文对 gain/pressure 估计、阈值标定、资源归一化等仍偏概念描述，不能仅凭公式认定全局最优，也不能据此精确重建全部实现。实现声称通过代理与 vLLM startup hook 完成，不修改 vLLM 源码。

## 4. 正确性：比“只缓存结果”更完整，但仍有条件

论文明确要求：无副作用工具才能直接投机；有副作用工具需安全变体，例如 dry-run 或 staging，否则不投机。结果在正式调用确认前与会话状态隔离。

这回答了“错误结果会不会提前进入 LLM 历史”，但严格等价还需要确认：

- **读取时机**：同一个 `read(file)` 在文件修改前后结果可能不同。无写副作用，不代表提前读取一定等价。
- **执行语境**：同名同参数还可能依赖工作目录、环境变量、权限、会话状态。规范化应覆盖哪些信息？
- **安全变体语义**：dry-run 的输出不自动等于正式执行的输出；staging 怎样验证状态并正式生效，需要工具级协议。
- **资源隔离**：低优先级和取消可以缓解竞争，但网络请求、CPU 缓存和不可即时抢占工作仍可能造成干扰。

以上是**适用条件核查**，不是断言论文实验出错。论文提供了安全策略和实测审计；尚不能由此推广为任意动态外部环境的形式化 lossless 保证。随机模型的逐次输出相同与分布保持，也需要分开定义。

## 5. 实验：优先保留有用证据

| 项目 | 论文设置或结果 |
|---|---|
| Agent / 任务 | VirtualLab、Qwen Deep Research、gemini-cli；ScholarQA、DeepResearchBench、SWE-bench |
| 模型 | Qwen-DeepResearch-30B；Qwen3-30B-A3B |
| 硬件 | 4 节点，每节点 8 张 A100 80GB，总计 32 GPU |
| 到达过程 | 回放 Azure Functions 时间戳，模拟突发请求；不是证明真实 Agent 请求具有完全相同分布 |
| 数据分离 | 作者称历史 pattern 挖掘与新任务评测不重合 |
| Baseline | vLLM、Agentix、ORION、SpecFaaS；未直接比较 SA 或 DSP |
| 端到端结果 | 正文称平均延迟最多降低 43.5%，p99 最多降低 55.4%；不要把 “up to” 写成所有设置平均 |
| 工具侧结果 | 相对 ORION 平均 1.71×，相对 SpecFaaS 1.83×；主要是观察到的等待时间缩短，不是工具本体计算必然变快 |
| 安全审计 | 超过 20,000 次投机中识别 602 次潜在副作用操作并阻止其提交；作者报告未发现最终结果不同 |
| 额外开销 | 一个中等预算设置使用额外 1–3 个空闲 CPU 核、250 MB 内存；预测和调度开销低于 100 ms，不能理解为所有配置统一上界 |

### 最有价值的消融

| 变体 | E2E 延迟 | 解释 |
|---|---:|---|
| PASTE-Tool-Only | 419 s | 只提前工具、没有 LLM 协调，返回突发加重负载 |
| PASTE-LLM-Only | 342 s | 不投机工具，使用 FCFS 准入控制减轻 GPU 过载 |
| 完整 PASTE | 270 s | 同时减少工具等待并管理 LLM 返回负载 |

**支持什么**：局部工具加速不保证端到端加速；联合控制在该设置中有效。

**还没分离清楚什么**：LLM-Only 使用 FCFS，并不等于“完整收益感知 co-scheduler 只关闭工具投机”。因此这组消融不能单独量化收益排序相对普通并发限制的贡献。后续若研究调度，必须加入 **Tool speculation + 调优后的简单准入控制** 作为强 baseline。

### 预测指标不能混读

作者报告最高 Top-1 27.8%、Top-3 43.9%、overall hit 93.8%。Overall hit 允许更多候选、随空闲资源扩大预算，因此不等于 Top-3，也不能据此说单候选已非常准确。

方法要求具体调用匹配，但实验文字对 accuracy 使用“tool matches”的表述。后续应确认是否严格包含全部参数，并同时记录：候选数、实际执行数、被复用比例、覆盖率、节省等待时间和浪费资源。**高命中可能来自多做工作，不能单独解释效率。**

## 6. 与前两篇的关系

| 维度 | Speculative Actions | DSP | PASTE |
|---|---|---|---|
| 核心路径 | 预测返回，预启动后续调用 | A 草稿与 T 多步规划验证并行 | 由历史模式绑定具体工具参数，提前执行 |
| 主要控制 | 候选宽度、置信度，也讨论深度 | 在线预测投机深度 | 候选效用、工具资源预算、LLM 返回调度 |
| 正确性入口 | 正式调用匹配后复用 | 顺序验证匹配前缀 | 每次正式调用匹配 + 安全工具策略 |
| 实验关注 | 多场景投机可行性 | 规划延迟和 token/费用 | 多会话 serving 的 E2E、排队和资源竞争 |

这不是三篇数值排名：实验任务、硬件和 baseline 不同，不能直接比较加速百分比。

## 7. 候选问题：收窄，而不是再造一个 PASTE

### P1：简单限流能解释多少联合调度收益？

**依据**：消融没有充分拆开“限制并发”和“按工具收益排序”。

**最小实验**：在固定轨迹和相同工具预测下，比较 FCFS+调优并发上限、完成会话优先、收益排序；保持相同预算，计入引擎外等待，测试平稳与突发两种到达。先做离线回放，不能用回放替代真实服务验证。

**放弃条件**：简单控制已足够；或者复现不出有意义的策略差距。即使简单基线赢，也先是分析结果，未必是一篇方法论文。

**难度与后续**：回放诊断低到中，vLLM 联调较高；不宜现在从零复制 32 GPU 全栈。继续核查 SPORK、AOSpec、AgentSpec。

### P2：调用匹配怎样升级为必要且低开销的状态验证？

**依据**：已知有副作用的调用可以禁止；提前只读操作的状态变化仍需明确。

**最小实验**：在可控文件工具上，固定动作名和参数，仅改变读取前后的文件版本；比较直接匹配、版本校验、完全不投机。先证明问题出现的条件，再测它在真实任务中是否常见。

**放弃条件**：后续系统已有同等保证；目标 workload 状态基本不变；或简单版本键已解决。事务/版本校验是既有技术，“增加状态 hash”本身不是创新。

**难度与后续**：最小例子低，全环境支持高。优先阅读 AOSpec、SMC，暂不建通用 rollback 系统。

### P3：多候选高命中是否值得其资源成本？

**依据**：最高 Top-3 与 overall hit 差距很大，候选预算影响解释。

**最小实验**：固定 pattern pool，扫描候选数与置信度阈值，画真实隐藏时间—浪费资源曲线，并按工具时长分组。

**放弃条件**：PASTE 的效用策略已覆盖且表现充分，或简单阈值即可解决。该问题并入已有 R1/R3，不另立“多候选调度”方向。

## 8. 本篇之后的判断更新

**排除宽泛 idea**：“加 memory/pattern”“考虑工具延迟”“负载感知投机”“加联合调度”。PASTE 已经做了。

**保留窄问题**：状态等价到底怎样验证；复杂调度超出简单基线的收益在哪里；指标是否真实反映每单位资源的收益。都要等待后续文献和小实验，不能现在声称新颖。
