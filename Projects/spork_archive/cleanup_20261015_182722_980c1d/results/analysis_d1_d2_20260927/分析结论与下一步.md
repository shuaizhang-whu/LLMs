# D1/D2 离线核查：结论与下一步

2026-09-27。分析对象：Qwen3-32B / τ² / 155 个任务 / baseline、D1、D1+D2。仅处理已保存的 465 份任务 JSON（2474 轮），没有运行模型或新任务。原始 JSON 及 summary 的 SHA256 前后相同。

## 1. 已修正什么

`spork_core/qwen.py::token_split` 原来必须同时找到工具调用开、闭标签。此次运行的 2009 次主模型工具调用都没有返回闭标签，导致工具 token 全记成 0，混入 `cot_tokens`。

现在将开标签至返回文本末尾计为未闭合工具片段，另记 `tool_call_closed` 与 `tool_call_parse_ok`，不虚构服务端省略的停止 token。完整 JSON 与截断 JSON 会被区分。完整闭合调用仍按原来的边界统计。

修正后工具片段 token 总计：baseline **27803**、D1 **26793**、D1+D2 **26128**。所有轮次的总 token 数与原记录相同，片段之和等于总数。5 项本地 tokenizer 回归检查通过。

`cot_tokens` 仍是兼容旧代码的名称：实际代表工具调用之前的文本，或无工具轮的全部文本，不能直接称为纯思考 token。上述计数来自重新分词保存文本，不是服务端实际生成 token 的完整账单。

## 2. 约 10% 的收益如何拆开

以下均为每任务均值。

|指标|baseline|D1|D1+D2|
|---|---:|---:|---:|
|端到端秒数|120.115|108.486|107.660|
|控制器记录的 main 边界耗时 / 秒|111.274|106.082|105.608|
|该边界至轮次结束 / 秒|8.793|2.336|1.947|
|轮次计时器之外 / 秒|0.048|0.068|0.105|
|日志估计的工具重叠 / 秒|0|6.220|6.712|
|主模型保存输出 token|3901.76|3708.70|3676.48|
|主模型工具调用次数|4.394|4.265|4.303|
|探针请求数|0|5.174|6.516|
|探针请求耗时之和 / 秒|0|5.801|8.249|

D1+D2 相对 baseline 的 **12.455 秒**平均节省，可按已有计时字段算术分为：main 边界前 **5.667 秒**、边界后 **6.846 秒**、其余 **−0.057 秒**。这不是因果分解。

原因：`main_end_ms` 在控制器等待探针之后、取得主请求结果时记录，不是独立的模型完成时间；`real_overlap_ms` 也使用这个边界估算。不能把 6.712 秒当成独立测得的准确物理重叠，更不能把其余 5.743 秒直接认作某一种机制收益。探针请求耗时与主解码并发，也不能直接从总收益中相减。

D1+D2 相对 D1：平均再省 **0.827 秒/任务**；多 **208** 次探针，复用次数从 **482** 增至 **521**；平均探针请求耗时之和增加 **2.448 秒**，日志重叠增加 **0.492 秒**。这提示 D2 增量值得单独检查，但单次记录不足以确认其稳定性。

另外，`spec_wasted` 漏掉了“探针已执行，但 Actor 最后直接回答”的情况：两种配置各漏记 **138** 轮。当前配置无 supersession，按 `spec_dispatched && !spec_used` 统计，D1 未复用 **308** 次、D1+D2 **274** 次，而原字段是 170、136。此处是未复用执行数，不等同于精确的浪费 GPU 时间或费用。

## 3. 轨迹差异定位到哪里

相对 baseline，两种投机配置各有 **104/155** 个任务的完整动作序列不同；其中各 **15** 个任务在第一轮就不同。第一轮差异中：6 个仅参数不同、5 个工具名称不同、4 个是“调用工具 / 直接回答”不同。不能把所有参数文本变化都等同于任务失败。

两种配置均有 **151/155** 个任务第一轮原始输出文本不同。代码路径为相同任务构建相同初始提示词，但旧日志未保存实际请求体或提示词 hash；因此服务批处理、数值路径、运行顺序等只是待验证原因。第一轮分歧发生在任何本任务工具结果提交之前，可排除“此前错误提交工具结果”作为这些第一轮分歧的原因。

三个可直接查看的例子（原文保存在 `selected_cases.json`）：

- **retail/43，第一轮，D1 与 D1+D2 均分歧**：baseline 直接询问更多信息；投机配置的 Actor 调用 `find_user_id_by_name_zip`。D1 探针猜的是 `get_user_details`，未被复用。变化已存在于 Actor 原文，非解析器把同一输出解释成不同动作。
- **airline/44，第三轮，D1**：baseline 查询 `get_flight_status`；D1 Actor 转人工。前两轮保存的动作、历史文本及工具结果长度/预览一致，第三轮探针虽预测 baseline 的查询动作，但不匹配 D1 Actor，因此未复用。完整工具结果和状态未记录，不能仅凭预览证明历史完全相同。
- **retail/75，第四轮，D1+D2**：baseline 直接执行换货，动作匹配得分 1；D1+D2 询问“Confirm exchange?”，得分 0，且没有复用换货探针。零售 policy 第 16 行要求修改数据库前取得明确确认，当前无用户模拟器。这是“动作匹配下降不必然等于行为质量下降”的具体例子，不能据此推广到所有失败任务。

全量检查中，重新解析的主动作与日志一致，独立 JSON 解码结果也一致；**1003 次复用**均满足日志记录的 gate 与名称/参数严格匹配。未发现这些可由日志核查的违例；这不等于完成了完整环境状态、隔离与并发安全证明。

成功任务数是 26、28、24。D1+D2 相比 baseline 有 9 个从失败变成功、11 个从成功变失败，净少 2 个；不是只发生了 2 个变化。单次运行不足以宣布稳定质量回退。该得分是本脚本的动作匹配检查，不是官方 τ² 用户模拟器评分。

## 4. 一个已确认、但影响仍待实验的问题

删除 `include_stop_str_in_output` 后，闭标签不仅从日志消失，还通过 `_append_tool_messages` 原样进入下一轮 assistant 历史。用实际 tokenizer/chat template 的轻量检查确认：模板不会自动补上闭标签。

**尚不能由此断言它导致了全部轨迹差异或 10% 收益。** 三种配置都使用这个格式，第一轮也尚无历史工具调用。后续应单独做历史格式修复的 A/B；不要无记录地改变行为再把新旧实验混合。

本次只修正计数，不改变模型请求、历史消息、gate、执行和参数解析行为。保留用户此前的调试修改。
