### 1.1 可截断窗口

【已核实】对 `results/controller_full_20261017_021939_Wid7sh` 中 155 个任务的
`timing_spork` 记录逐回合统计（614 个有工具调用的回合，478 个投机命中）：

| 指标 | 数值 |
|---|---:|
| 投机命中率 | 77.9%（478/614） |
| 命中回合的 slack（`main_end_ms - spec_end_ms`）中位数 | 48.1 s |
| 同分布 P90 | 89.3 s |
| 最大 | 196.8 s |
| slack 占全部回合解码时间 | 64.2% |
| slack 占命中回合解码时间 | 90.0% |
| slack > 5 s 的命中回合 | 476/478 |

注意：`tool_result_ready_ms` 记录的是主线程取到结果的时刻（命中回合等于 main_end 之后几毫秒），
不是工具真正完成的时刻。真正的完成时刻是 `spec_end_ms`。上一轮 `protocol.json` 里的
`matched_tool_ready_slack` 口径需要按此修正。

### 1.2 探针成本与 D3 复用

【已核实】预检 `results/reused_probe_preflight_20261021_a`，2 个训练前缀 × 3 次重复：

| 模式 | 生成完整调用耗时 | 说明 |
|---|---:|---|
| plain（重新生成） | 3.45–3.62 s | 42–43 个 token |
| d3（复用已有候选作草稿） | 1.53–2.23 s | 20/20 草稿 token 被接受 |
| 单 token 自由探针 | 0.165–0.170 s | `p(<tool_call>)` |

【已核实】同一候选下，plain 与 d3 的 token 序列和解析动作完全一致；每次探针节省 1.4–1.9 s。
D3 计数器无 dropped injection、无 prefix mismatch、无 accounting error。

### 1.3 首探针的错误结构

【已核实】614 个工具回合中：

- 478 个命中（名字与参数都正确）；
- 38 个名字正确、参数错误；
- 98 个名字错误。

【已核实】136 个未命中回合中，109 个只跑了 1 个探针（首探针置信度 ≥ 0.9，直接 dispatch 后 break），
因此现有记录无法判断这些回合的调用在更晚位置是否会收敛。27 个多探针未命中回合里，
15 个首探针名字错误，后续探针均未纠正名字。样本很小。

【已核实】首探针的 `span_confidence` 对命中/未命中几乎没有区分度（中位数均接近 1.0）。
这与 ETA 论文 Fig.2(c) 的结论一致：强制探针置信度不能作为退出信号。

## 2. 候选嫁接矩阵

### A. ETA 式提前退出（当前主攻）

【论文陈述】ETA 把投机 fork 从「执行器」改造成「决策状态传感器」：每隔 Δ=50 token 跑一次
强制探针 + 一次自由探针；当最近 k=3 次预测完全相同、自由探针 `p(<tool_call>) ≥ τ=0.9`、
且工具已就绪时，截断主模型推理，只追加 `</think>`，让模型自己生成最终动作；若续写没有动作则回滚。
τ² 上 1.33×，解码 token 少 27%，动作质量非劣。

【推导】我们的 slack 占比 64.2%，高于 ETA 报告的 38.9%，因此理论上限更高；若能在命中回合
平均截掉一半 slack，整体加速约 1.4–1.6×。

【待验证】在 4×3090 + batch-invariant 服务上，ETA 的 8 次重复强制探针会与主解码争抢算力，
可能把「无退出」回合拖慢。需要 `ours(off)` 对照量化。

### B. D3 复用探针（A 的低成本化）

【推导】把已经 dispatch 的候选调用注册为 D3 草稿，重复稳定性检查从 3.5 s 降到 1.7 s 左右；
token 与动作完全一致。这样每次检查的成本减半，可支持更密的检查或降低无退出回合的 overhead。

【已核实】2026-10-21 冒烟 `retail_0_r0_eta.json` vs `retail_0_r0_reuse.json`：
ETA 的 5 次检查每次 `_forced` 约 3.85–3.9 s，reuse 的 `decision_probe` 每次约 2.9 s，
单次省约 1 s；但两者整回合 wall time 几乎相同（47.51 s vs 47.12 s），
因为探针与主解码重叠，探针不在关键路径上。

【推导】D3 复用/分层探测的主要价值不是直接减少 wall time，而是降低同卡 GPU 争用：
在更快的主解码、更高并发或更弱 GPU 上，探针成本会重新进入关键路径。
当前 4×3090 batch-1 场景下不应把它当作主要卖点。

### C. 分层稳定性探测（ETA + ToolSpec 的 schema 先验）

【推导】ETA 每次检查都要重新生成完整 JSON 调用。但工具名是 schema 定义的闭集，
参数是开放值。可以用一次自由探针（0.17 s）判断「是否会调用工具」，再用一个只生成工具名的
短探针（受 `{"name": "` 前缀约束，约 0.2–0.4 s）判断「调用是否仍是同一个工具」；
只在准备截断前做一次完整调用校验。这样每次检查从 3.5 s 降到约 0.5 s，
同时保留完整参数校验作为最终门。

【待验证】名字稳定但参数仍在变化的回合比例；需要离线统计或在线冒烟。
若比例低，分层探测几乎不损质量；若比例高，需要更严格的最终门（连续两次完整校验）。

### D. 退出感知的 re-dispatch（A + SPORK D2）

【推导】SPORK 在第一次高置信 dispatch 后 break；ETA 要求后续预测与已 dispatch 的调用一致，
因此首探针错误的 136 个回合完全无法退出。但退出循环本来就会继续探测；如果连续 k 次探测
收敛到另一个调用，可以取消旧的投机执行、dispatch 新调用，从而把这些回合也纳入退出范围。

【已核实】现有 27 个多探针未命中回合中，15 个首探针名字错误且后续未纠正；但 109 个
「首探针高置信但错误」的回合没有后续探测数据，机会大小未知。

【已核实】2026-10-21 冒烟 `airline_2_r0_eta.json` 给出了第一个直接证据。该回合首探针在
token 1 预测 `search_direct_flight`（错误），真实调用是 `get_user_details`。ETA 的 8 次检查：

| 检查 | token | p(<tool_call>) | 预测调用 | 与首探针一致 |
|---:|---:|---:|---|---|
| 1 | 81 | 0.947 | `get_user_details`（真实） | 否 |
| 2 | 161 | 0.979 | `get_user_details` | 否 |
| 3 | 241 | 0.990 | `get_user_details` | 否 |
| 4 | 321 | 0.661 | `get_user_details` | 否 |
| 5 | 396 | 0.978 | `get_user_details` | 否 |
| 6 | 476 | 0.944 | `search_direct_flight`（回摆） | 是 |
| 7 | 556 | 0.965 | `get_user_details` | 否 |

【推导】若在 token 81 发现稳定调用与已 dispatch 调用不同时立即 re-dispatch，
token 81/161/241 三次一致即可在约 28 s 处触发退出（真实回合 185 s），该回合可省约 85%。
但检查 6 的回摆说明调用并非单调收敛，re-dispatch 需要保留「再次 supersede」的能力，
且必须以真实动作的最终 exact match 作为提交门。

【已核实】并行会话实现的 `spork_core/stable_refresh_exit.py` 已把这一机制落地，规则为：

1. 每个 50-token 检查点跑一次自由探针（是否调用工具）和一次强制探针（调用是什么）；
2. 候选必须同时满足自由探针 p ≥ 0.9、强制探针置信度 ≥ 0.9、调用非空；
3. 连续 `stable_checks=3` 次候选完全一致后，若与当前已 dispatch 的调用不同，
   且旧投机执行已完成，则取消旧候选、dispatch 新候选（最多 `max_refreshes=1` 次）；
4. 刷新后稳定计数立即达到阈值，工具就绪且到达句界时截断；
5. 最终动作仍由模型自己生成，只有与当前 dispatch 调用 exact match 才复用投机结果。

【已核实】两组独立冒烟结果（同一 8017 服务，2 s 工具下限，固定 seed 42）：

| 任务 | SPORK | ETA | refresh | 省时 | 质量 |
|---|---:|---:|---:|---:|---|
| airline:2（首探针错） | 185.12 s | 188.38 s | 36.60 s | 148.5 s（5.06×） | 动作/状态/最终答案一致 |
| retail:0（首探针对） | 65.45 s | 47.41 s | 47.41 s | 18.0 s（27.6%） | 动作/状态/最终答案一致 |

【推导】refresh 不改变命中回合的行为（与 ETA 相同），只在「首探针错误但后续稳定到另一个调用」
的回合解锁退出。按现有 930 次运行数据，这类回合占全部工具回合的 22.1%，占任务的 58.0%，
因此整体加速可能显著高于 ETA 的 1.33×。

【待验证】8 任务扩大冒烟（airline:2/3/4/6、retail:0/1/3/4）正在进行；
重点是 retail:3 这个第二个未命中任务，以及 `off` 轨迹里「首次 3 连稳定调用」与最终动作的一致率。

### E. ObsSpec 式观测预测

【论文陈述】用小 world model 预测工具输出，让策略模型提前开始下一轮；精确匹配才保留。
0.6B world model 的观测精确匹配率 66.4%，8B/32B 策略延迟分别降约 9.3%/14.2%。

【已核实】本地数据中命中回合的工具在 main_end 之前约 48 s 就已完成，工具不是瓶颈。
【推导】在 τ² + 2 s 工具下限的负载上，观测预测几乎没有额外可隐藏的窗口；优先级最低。

### F. DLite / ProSpect / CTES / SpecAgent

- DLite：需要 target hidden states 和引擎内 drafter，当前 HTTP 服务拿不到 hidden states；
  工程量大，暂不作为本轮候选。
- ProSpect：多 Agent DAG 路由；τ² 单 Agent，不适用。
- CTES：预 draft 预算 + 后 draft 选择；其「生成前门控」与我们失败的 BERT 启动控制器同构，
  但目标是 token 预算而非 wall time；暂不作为主攻。
- SpecAgent：read-only 立即执行、写操作才审查；其「语义接受」不保证观测一致，
  在 τ² 的状态型任务上有风险；可作为 D 的语义扩展备选。

## 3. 当前冒烟

`scripts/run_early_exit_smoke.py`，2 个训练任务（airline:2、retail:0）×
{spork, eta, reuse} × 1 轮，工具下限 2 s，固定 seed 42。

已修复的 runner 问题：

1. aiohttp 复用 uvicorn 5 s keep-alive 连接导致 `/spork/clear` 断连；改为 `force_close=True`。
2. `launch_mode="spork"` 不是合法枚举；原始 SPORK 应为 `"original"`。

【已核实】第一轮结果（`results/early_exit_smoke_20261021_e`）：

| 任务 | SPORK | ETA | reuse | 动作/结果/状态一致 |
|---|---:|---:|---:|---|
| airline:2（首探针错误） | 184.75 s | 187.17 s | 187.06 s | 是 |
| retail:0（首探针正确） | 65.52 s | 47.51 s | 47.12 s | 是 |

- 命中回合省 18.0–18.4 s（27.5–28.1%），退出在 token 358 触发，无回滚、无错误。
- 未命中回合只慢 2.3–2.4 s（1.3%），说明探针与主解码重叠良好。
- 但这 2 个任务不足以证明质量非劣，只能排除灾难性分叉。

【已核实】并行会话在 `spork` 树中实现了同一假设的 `stable_refresh_exit.py`：
要求候选连续 `stable_checks` 次一致、自由探针 p ≥ τ、强制探针置信度 ≥ 0.9、
旧投机执行已完成，最多刷新 1 次；正在跑 airline:2 / retail:0 的 spork/eta/refresh 冒烟。
本轮结束后应先读它的结果，再决定是否把 `redo` 与 `refresh` 合并为同一实现，避免重复。

【待验证】刷新后的退出在更多未命中任务上的质量与收益；尤其要按「初始命中/未命中」分组报告。
