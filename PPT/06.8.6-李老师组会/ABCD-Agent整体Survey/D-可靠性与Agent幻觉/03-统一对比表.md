# D．可靠性与 Agent 幻觉：统一对比表

| 方法 | 研究粒度 | 幻觉/错误定义 | 数据/干预 | 核心指标与结果 | 是否缓解 | 主要局限 |
|---|---|---|---|---|---|---|
| MIRAGE-Bench | action snapshot | 不忠实于 task、history 或 observation | 多交互 benchmark 风险点 snapshot | risk-aware utility / hallucination rate；各模型均有显著风险 | 否 | 静态 snapshot 不等价于完整 rollout；依赖 LLM judge |
| AgentHallu | step attribution | 5 类 14 子类，找最早 responsible step | 693 trajectories，7 agent frameworks | 最佳定位 41.1%；tool-use 仅 11.6% | 否 | 数据规模有限；强 judge/人工成本高 |
| AgentDebug | module/root cause | memory/reflection/planning/action/system failure | 200 专家标注失败轨迹；critical-step rerollout | detector step/all-correct 提升；下游 success 相对最多提升 26%（论文报告） | 是 | general failure 不全是 hallucination；重跑成本高 |
| Reasoning Trap | single tool decision / representations | 无工具或只有 distractor 时仍编造/误用 | RL、蒸馏、thinking on/off 控制实验 | reasoning 提升与 tool hallucination 同步上升；DPO 缓解但损 utility | 部分 | 合成、单步场景；因果机理仍需扩展到长轨迹 |
| Relign | tool trajectory | type/timing/format/content 四类 | RelyToolBench；SFT+DPO；ChangeTools/TalkToUser | 多个 7B/8B baseline THR 约 49–57 降到约 15–18 | 是 | 依赖 GPT-4o evaluator；timing hallucination 改善较小 |
| AgentProp-Bench | parameter→trace→final | schema 合法但语义错误参数的传播 | 2,000 tasks/2,300 traces；运行时 L1–L3 interceptor | substring judge κ=.049；3-LLM κ=.432；传播约 .62；GPT-4o-mini hallucination -23pp | 是 | 缓解对模型/失败模式敏感；工具多为确定性模拟 |
| TIM / From Proof to Program | reasoning process | 工具输出替代必要推理，解释不再被证明支撑 | PyMath 1,679；Code Interpreter | final accuracy 可升，但过程 win/miss/PRM 变差；高风险约 55% TIM | 部分 | 数学/代码解释器为主，不是通用 Agent 动作 |
| Trajel | subtask/trajectory | factual/referential/logical/procedural/scope | 225 工业多 Agent 轨迹 | 68.3% human hallu；近半多类型；LLM judge binary F1 .855 | 否/审计 | 单域小数据；细类型标注一致性和模型性能较低 |

## 关键分析

- “最终答对”不足以证明轨迹可靠：TIM 与 Trajel 都显示过程可能失真。
- “检测到错误”不等于“知道根因”：AgentHallu 的 step localization 远低于二分类。
- “更强推理”不等于“更会拒绝不可能任务”：Reasoning Trap 给出反例。
- 缓解有两条互补路线：Relign 改 policy 的 action space；AgentProp/GUI-Critic/VeriGUI 在 runtime 加守卫。
- Judge 本身必须评估：κ、precision/recall、跨模型迁移和干预成本都不能省略。
